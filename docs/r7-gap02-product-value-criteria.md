## 0. 기준 시점 — 문서와 HEAD 의 차이 (먼저 읽을 것)

기준 문서는 **`e032dc3` 까지의 제출 보고**를 전제로 쓰였다. 실제 HEAD 는

| 문서의 전제 | 실측 결과(`6a27e57`) |

| §5.3 가설 "제목을 바로 바꾸지 않음" | 제목 `근무 가능일 선택` **KEEP** 으로 결정(독립 용도 확인이 근거) |

|---|---|---|---|
| `_dispatchToMatchNotifications` | `city == 사업장 도시` + `dates array-contains 날짜` | **없음** | ACTIVE(호출부 4곳) |

**초대 = 사용자가 고른 `inviteRegionKeys`**. 하나로 설명하면 틀린다.

## 1. 이 기준이 기존 감사에 더하는 것

기존 R7-P1/P2 는 **CODE·행동·RENDER** 를 닫아 왔다. 이 기준이 추가로 요구하는
것은 다음 세 가지이고, 셋 다 **아직 증거가 없다**:

1. 이해와 시작 — 처음 온 사람이 이득을 알고 설정을 **스스로** 끝내는가
2. 실제 업무 완수 — 설명해 주는 개발자 없이 역할 간 일을 넘기는가
3. 반복 사용의 가치 — 전화·엑셀 대비 총수고가 줄어드는가

→ 이 세 가지는 **USER OBSERVATION / 운영 파일럿** 등급의 증거를 요구한다.
`flutter test` 수·RENDER 통과·CODE 계약은 **대체 증거가 아니다.**
현 시점 네 역할 모두 **PRODUCT OPEN** 이다.

## 4. 이 기준으로 바뀌는 보고 규칙

- `CODE → RENDER → DEVICE` 를 **자동 승격 단계로 쓰지 않는다.** 각 등급은
  서로 다른 것을 입증한다(기준 문서 §7 표).
- "사용자가 이해한다" 는 **관찰이 있을 때만** 쓴다. 없으면 HEURISTIC 으로 표시하고
  "사용자가 모른다" 는 확정 결론도 쓰지 않는다.
- 문구와 계약이 다르면 관찰을 기다리지 않고 고친다(이미 그렇게 해 왔다).
- 테스트 총수·PASS 수를 제품 가치의 대리 지표로 쓰지 않는다.
- 역할별 표본을 합쳐 성공률을 높이지 않는다. 관찰하지 못한 역할은 **PRODUCT OPEN**.

## 5. 현재 결산 — 네 역할

| 역할 | CODE/RENDER | USER OBSERVATION | PRODUCT |
|---|---|---|---|
| 지원자 | P2-1·P2-2·P2-3 종료(잔여 명시) | **없음** | **OPEN** |
| 관리자 | P1-2~P1-7 종료(DEVICE 대기) | **없음** | **OPEN** |
| 서브관리자 | 권한 계약 CODE · 모드 토글 실측 | **없음** | **OPEN** |
| 슈퍼관리자 | shell 11/11 · 일부 CODE only | **없음** | **OPEN** |

**본 문서는 파일럿 운영·실데이터 쓰기·권한 확대를 승인하지 않는다.**
공유 DEV READ ONLY 와 기존 release gate 는 그대로다.
