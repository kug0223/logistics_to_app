## P31-H — 관리자↔지원자 인계 (일반 초대)

### 고른 사건

한 사업장·한 날짜·한 업무에서 **일반 초대**(비요청 대상 발견) 한 벌.
`callableOfferAlternativeWork`(기존 지원자 대상 **대체 제안**)와 **분리해서** 본다 —
호출도 화면도 다르다.

| 단계 | 화면·소스 | 사용자에게 보이는 원문 |
|---|---|---|
| 관리자 후보 찾기 | `available_workers_bottom_sheet.dart` (`callableGetAvailableWorkers`) | 후보 0일 때 **`이 지역의 근무 초대를 받도록 설정한 인력이 아직 없어요.`** |
| 관리자 발송 전 | 같은 시트 `_invite` 확인 다이얼로그 | `근무 제안` / `{마스킹이름}님에게 {M월 D일} {업무} ({HH:MM}~{HH:MM}) 근무 제안을 보내시겠습니까?` / CTA `제안 보내기` |
| 관리자 발송 후 | 토스트 | `근무 제안을 보냈습니다.` |
| 지원자 수신·수락 | `my_applications_screen.dart` 수락 다이얼로그 | `이 업무에 참여하시겠습니까?` + **`수락 후 일정 충돌이 없으면 확정됩니다.`** / CTA `동의하고 초대 수락` → `초대를 수락했습니다!` |
| 지원자 거절 | 같은 화면 | `초대 거절` / `초대를 거절하시겠습니까?` → `초대를 거절했습니다.` |
| 관리자에게 돌아온 상태 | `day_applicants_dialog.dart` | `초대 수락 · 확정` / `초대 거절` / `초대 철회` — `acceptedInvites`·`closedInvites` 로 분리 보관 |

### 판정

- **자동 근무 확정을 약속하지 않는다.** 관리자 쪽은 처음부터 끝까지 `제안`이고,
  지원자 쪽은 `수락 후 **일정 충돌이 없으면** 확정됩니다` 로 **조건**을 말한다. PASS.
- **후보 자격을 거주지가 아니라 초대 동의로 말한다.** 빈 후보 문구가
  `이 지역의 근무 초대를 받도록 설정한 인력` 이다 — P2-3 에서 확인한 서버 자격
  (`inviteEnabled` + `inviteRegionKeys` + `dates`)과 **같은 말**이다. PASS.
- **초대를 보낸 쪽이 그 초대가 어떻게 끝났는지 안다.** 확정자 명단에 섞여
  사라지지 않고 `invitedAt` 으로 `초대 수락 · 확정` 이 유지된다. PASS.
- **거절의 주체가 구분된다.** 같은 `REJECTED` 값인데도 지원자 화면은
  `invitedAt` 으로 **`초대를 거절했어요`(내가)** 와 **`이번 지원은 확정되지
  않았어요`(관리자가)** 를 나눈다. PASS.
- **타인 데이터:** 관리자 확인 문구의 이름은 `maskedName` 이다.

### 미실행

실제 발송·수락·확정 **writer 성공과 FCM 전달은 실행하지 않았다.**
공유 DEV READ ONLY 경계다. 위 표는 **소스 원문 + 기존 렌더 증거**이며
실제 mutation 은 VJ03/VJ04 의 기존 잔여로 남는다.

## P31-D — 서브관리자

### 먼저 확정한 구조

**`SUB_ADMIN` 이라는 role 은 없다.** `enum UserRole { SUPER_ADMIN, BUSINESS_ADMIN, USER }`
뿐이고, 서브관리자는 **`USER` + 비어있지 않은 `subAdminBusinessIds`** 다
(`UserModel.isSubAdmin`). 그래서 "본인 근로 화면으로 전환"은 다른 계정으로
가는 것이 아니라 **같은 계정의 모드 토글**(`isAdminMode`)이다.

### 대표 과제 (실제 capability 에서 선정)

| | 과제 | 권한 | 제한 시 보이는 것 |
|---|---|---|---|
| **허용 1** | 근로자 승인·출퇴근 관리 | `canManageWorkers` | — |
| **제한 1** | 급여 확인·정산 | `canManageWage` 없음 | 토스트 **`급여 관리 권한이 없습니다.`** 뿐 |

### 발견 — 같은 "권한 없음"이 화면마다 세 모습이다

| 기능 | 제한 표현 | 이유 | 담당자 안내 | 복귀 |
|---|---|---|---|---|
| 계약 관리 | 화면이 **열리고** 빈 상태 | `접근 권한이 없습니다` | **있음** — `계약 관리 권한이 있는 관리자에게 문의하세요.` | 화면 뒤로 |
| 급여 | 탭하면 **토스트만**, 화면 미개방 | `급여 관리 권한이 없습니다.` | **없음** | 제자리 |
| 팀원 관리 | 메뉴 **자체가 없음**(`user?.isBusinessAdmin == true` 게이트) | 보이지 않음 | 없음 | — |

팀원 관리가 없는 것은 **설계 의도**다(권한 부여 = 이양, 멤버 관리는 SubAdmin
완전 제외). 거짓 완료도 타인 데이터 노출도 아니다.
급여 쪽에 담당자 안내가 없는 것은 **거짓이 아니라 부재**다 → 수정하지 않고
**VERIFY 후보**로 올린다(P31-F).

### VJ11 역할 전환 — 실제 렌더로 확인함

| 방향 | 입구 | 깊이 | 증거 |
|---|---|---|---|
| 지원자 → 관리자 | **MY 탭** `관리자` 섹션 · `관리자 모드로 전환` (사업장 2개 이상이면 `관리자 사업장 선택`) | 1단계 | **RSW-1** |
| 관리자 → 지원자 | **설정** `서브관리자 관리` 섹션 · `지원자 모드로 전환` | 2단계 | **RSW-4** |

- 서브관리자가 아니면 들어가는 입구가 **아예 없다**(RSW-2, 양성 대조 `프로필 관리` 생존).
- 나오는 문은 MY 탭에 **없다**(RSW-3) — 두 문의 **깊이가 다르다**.
- `서브관리자 관리` 섹션과 `서브관리자 탈퇴` 는 모드와 무관하게 있고,
  **복귀 CTA 만 관리자 모드일 때 나타난다**(RSW-4 가 양쪽 모드로 대조).

이 비대칭은 **결함 판정이 아니다** — 나가는 길은 존재하고 이유도 분명하다.
실사용자 관찰이 없으므로 "찾기 어렵다"고 **결론내지 않는다**(HEURISTIC).

### 내 근무·내 돈과 관리자 데이터가 섞이는가

`settings_screen` 은 두 모드가 **공유**하는 화면이고, 관리자 항목은
`showAdminSection = role == BUSINESS_ADMIN || isSubAdminInAdminMode` 로 갈린다.
지원자 모드에서는 관리자 섹션이 **빌드되지 않는다**. CODE + RSW-4 의 모드별 대조.
**지원자 모드의 데이터 스코프 자체(내 지원·내 수입)를 실제로 렌더해 비교하지는
않았다 → NOT SEEN.**

## P31-X — 슈퍼관리자

### 대표 과제 (실제 제공 화면에서 선정)

| | 과제 | 화면 |
|---|---|---|
| **대상 조회 1** | 계정 문의가 들어온 사람 찾기 | `all_users_screen.dart` |
| **운영 설정 1** | 공고 등록 개수 한도 조정 | `to_limit_settings_screen.dart` |

### 대상 조회 — 동명이인·사업장 범위

- 검색은 **이름 · 아이디(`username`) · 연락처(`effectivePhone`)** 를 본다
  (힌트 원문 `이름 · 아이디 · 연락처 검색`). 역할 필터는 `ALL` + 역할별 `(개수)`.
- 카드에 `user.name` 과 **`@{username} · {역할}`** 이 함께 뜬다 →
  **동명이인은 `@아이디` 로 갈린다.**
- **사업장 범위는 `businessName` 이 있을 때만 뜬다.** 지원자(USER)에게는 이 값이
  없으므로, **"이 사람이 어느 사업장에서 일했는가"는 이 화면에서 알 수 없다.**
- 가능한 조치는 **블랙리스트 해제 · 제재 해제** 이며 확인 문구가 결과를 말한다
  (`해제 후 로그인이 가능해집니다.` / `해제 후 즉시 이용 가능해집니다.`).
  **실행하지 않았다.**

### 운영 설정 — 전역/대상 한정, 신규/기존

- 화면이 **두 탭으로 전역과 개별을 구분**한다: `전역 기본값`
  (`settings/app_config.maxActiveTOPerBusiness`) · `관리자별 한도`
  (`users/{uid}.maxActiveTOs`, null 이면 전역).
- 우선순위를 **문구로 말한다**: `관리자별 개별 한도가 설정되지 않은 경우 이 값이
  적용됩니다.` · 행 배지 `개별 N개` / `전역 N개` · 입력 힌트
  `비워두면 전역값(N개) 사용`. **전역/대상 한정 구분은 화면에서 알 수 있다. PASS.**
- **예외도 말한다**: `draft 상태로는 제한 없이 저장 가능합니다.`

**화면이 말하지 않는 것 세 가지 (거짓이 아니라 부재):**

1. **단위.** `4개` 라고만 쓴다. 서버 강제는 `status in [ACTIVE, FULL]` 인
   **유효 활성 공고 수**이고, scope 는 `ADMIN:{ownerUid}` — 즉 **그 오너의 모든
   사업장을 합친 수**다. 사업장당이 아니다.
   (Firestore 필드명 `maxActiveTOPerBusiness` 는 이 점에서 **이름이 낡았다**.
   다만 **사용자에게 보이는 문구는 "사업장당"이라고 말하지 않는다** — UI 는 틀리지 않았다.)
2. **기존 공고의 운명.** 강제 지점은 `callableCreateTO` 의 **생성 시점**이다
   (`getEffectiveActivePostingCountTx`). 한도를 낮춰도 이미 열린 공고는 닫히지
   않고 **신규 생성만 막힌다.** 화면에 그 말이 없다.
3. **대상의 현재 사용량.** 행에 뜨는 수는 `{N}개 사업장 관리 중` — **사업장 수**이지
   한도가 세는 **활성 공고 수가 아니다.** 지금 한도를 넘었는지 모르고 값을 정하게 된다.

→ 셋 다 **VERIFY 후보**. 기능을 추가하지 않는다.

### 등급

`all_users_screen`·`to_limit_settings_screen` 모두 **CODE(소스 원문) only**.
**이 두 화면의 내용 RENDER 는 실행하지 않았다 — NOT SEEN.**
